Executive Read

What Phase 2 is really doing

Phase 2 turns a working football slice into a safer, clearer, more football-native product surface before content expansion. It should retire bridges only when validation proves the playable loop remains stable.

Biggest release blocker

Portrait and likeness strategy. TheSportsDB-style cutouts are acceptable for internal demos only. Public-facing paths need owned, licensed, or stylized local assets.

Biggest engineering risk

Touching shared UI and legacy bridge names too broadly. Scout, swap, badge, album, and save changes must stay atomic and preserve the vanilla runtime.

Core Assumptions

  • A1 · Continuity beats ideal architecture

    The game must remain playable after every task. Phase 2 improves seams incrementally instead of replacing the vanilla app or forcing React/Next early.

  • A2 · Cloud save remains off

    Cloud support is not a Phase 2 feature. Any account hardening must be local-first and avoid adding game_album to legacy cloud sync keys.

  • A3 · No runtime live API dependency

    External APIs may exist as manual/offline sync tools only. Boot, cards, album, save/load, and settlement must work without TheSportsDB, PokeAPI, or network availability.

  • A4 · Battle math is stable

    Phase 2 can improve labels, adapters, and visual presentation, but battle formulas should not change unless a task explicitly scopes balance work.

  • A5 · Expansion waits for quality gates

    Maps 3-7 should not be enabled until current 3-city manual QA, portrait strategy, no-live-API gate, and UX polish are green.

Tradeoffs To Keep Visible

  • Bridge aliases before deletion

    Adding football-named album APIs while keeping legacy dex aliases reduces regression risk. The cost is temporary duplicate naming in code.

  • Local asset manifest before final art

    A local manifest can break runtime dependence on remote cutouts before final portraits are ready. The cost is that early visuals may still be placeholder-quality.

  • HTTP smoke, not screenshots

    Phase 2 can verify static boot and asset availability without screenshot automation. Manual QA remains responsible for visual judgement.

  • CSS selector aliases

    Stamp and recruitment screens may need compatibility aliases while handlers migrate. Remove player-facing legacy copy first, then retire selectors after checks pass.

  • Manual QA before content expansion

    Manual loop QA takes time but prevents multiplying defects across eight host cities and future knockout flow.

  • Public release safety over demo fidelity

    Stylized local placeholders are preferable to attractive but legally unsafe third-party likenesses on any release-critical path.

Execution Watchlist

Do not widen scope early

If a polish task exposes content-expansion needs, record the dependency and stop. Do not enable maps 3-7 as a side effect.

Preserve old aliases until proven safe

Bridge retirement should prefer football-named APIs plus compatibility aliases, then later grep-backed deletion.

Keep UI and save separate

Recruitment or album visual improvements must not alter persistence semantics unless a dedicated save task owns the change.

What The Owner Should Know

  • Do not confuse internal demo-ready with release-ready

    The playable loop can be solid while asset rights are still unresolved. That is acceptable only if release claims stay blocked.

  • Manual QA is now a gating activity

    Phase 1 was signed off by scripts. Phase 2 should not expand content before someone records the real 3-city loop, reload, full-squad, and loss paths.

  • The easiest bad decision is deleting bridges too soon

    Legacy names are ugly but some still protect shared runtime behavior. Retire them with tests, not by search-and-replace.
