SPEC 011 Phase 1 assumptions, tradeoffs, and design decisions

This report records the engineering assumptions made outside the written specs, plus the practical tradeoffs and localized design decisions that should guide Phase 1 implementation. Task-level entries should be appended as each SPEC 011 ticket lands.

Scope: Phase 1 vertical slice only No gameplay redesign Minimize file changes Working game after every task

Operating Assumptions

Task discipline

Each SPEC 011 task is treated as an isolated ticket. If dependencies are incomplete, implementation stops instead of partially building future work.

Compatibility first

The vanilla engine remains the source of truth for battle flow, map traversal, save/restore shape, and screen transitions unless a Phase 1 ticket explicitly changes the boundary.

Football-only slice

Phase 1 assumes football mode is the active experience, but legacy Pokelike code paths stay in place behind feature gates rather than being deleted.

Assumptions Outside The Specs

  • No build tooling will be introduced All new code should work through plain script tags, browser globals, and static JSON fetches. This keeps the Phase 1 demo aligned with the current project shape.
  • Domain modules use globals for now Because the existing app is not bundled, new domain modules should attach stable namespaces to window while keeping logic portable enough to copy into a future TypeScript domain layer.
  • Existing active saves may be imperfect Migration should be defensive for missing fields, but it should not try to convert an old active run into a football run. Fresh football runs are the supported Phase 1 path.
  • Catalog fetch errors are recoverable If JSON cannot load, the title screen should fail visibly and block new runs instead of falling back to Pokemon data or starting with incomplete football content.
  • CSS additions should be additive New football card, album, and stamp styles should avoid large rewrites of existing CSS. Legacy selectors can stay as long as football screens render correctly.
  • Manual QA is acceptable for Phase 1 Automated tests are valuable, but the task breakdown treats manual smoke tests as the Phase 1 gate. Test scripts should not block small implementation tickets unless a ticket asks for them.

Task-Level Assumption Log

  • P1-001 — Create domain/features.js with Phase 1 flags

    Status: implemented
    Assumptions

    The existing browser-global runtime is the correct integration style for Phase 1. A single global FEATURES object is enough until later tasks introduce consumers.

    Tradeoffs

    Object.freeze() makes accidental runtime mutation less likely, but it also makes console-based flag toggling less convenient during manual QA.

    Design Decisions

    Keep features.js dependency-free and load it immediately before data.js. Do not add the remaining domain stubs as part of this task.

    Risks / Follow-up

    Low risk now because no runtime consumers read FEATURES yet. P1-002 must preserve script order when adding the remaining domain modules.

  • P1-002 — Scaffold remaining js/domain/ module shells

    Status: implemented
    Assumptions

    Empty frozen namespace objects are sufficient no-op exports for this stage because no later code should call domain APIs until their task explicitly implements them.

    Tradeoffs

    Loading inert scripts early validates the target script order now, but it also means any syntax error in a future stub can break boot before the module is functionally used.

    Design Decisions

    Use one stable Domain* global per module and keep every shell dependency-free. The task intentionally stops before adding style IDs, catalog loaders, album APIs, save migration, or recruitment behavior.

    Risks / Follow-up

    Low risk while the exports are empty. P1-003 should replace only DomainStyles internals and preserve the established load order.

  • P1-003 — Implement StyleId enum and STYLE_CHART

    Status: implemented Review: PASS
    Assumptions

    The current legacy TYPE_CHART has 17 keys, while the football domain requires 18 StyleId keys. Phase 1 can preserve balance by projecting styles through a temporary legacy mapping.

    Tradeoffs

    set_piece_master temporarily shares the neutral Normal matchup profile. This avoids inventing new combat math before P1-004, but it must be revisited when the battle engine consumes native style keys.

    Design Decisions

    Keep all style work inside domain/styles.js, expose globals for the current script runtime, and provide verifyStyleChartParity() so drift can be checked without modifying data.js.

    Risks / Follow-up

    Medium design risk if the temporary set_piece_master mapping becomes treated as final. P1-004 should reduce drift by making data.js consume or re-export the domain style system.

  • P1-004 — Wire STYLE_CHART into data.js

    Status: implemented Review: PASS
    Assumptions

    The battle engine can keep calling getTypeEffectiveness(); the compatibility split belongs in data.js, not in battle.js.

    Tradeoffs

    Football mode accepts both native StyleId values and legacy type strings during transition. This prevents immediate adapter churn but keeps temporary mapping logic in data.js.

    Design Decisions

    Non-football mode continues reading TYPE_CHART. Football mode reads STYLE_CHART from the domain globals and leaves MOVE_POOL unchanged for the slice.

    Risks / Follow-up

    Low risk after branch verification. Later cleanup can add explicit data.js aliases if future callers expect style constants from the data layer rather than DomainStyles.

  • P1-010 — Implement createPlayerInstance() in domain/combat-adapter.js

    Status: implemented Review: PASS
    Assumptions

    The safest Phase 1 boundary is a plain runtime adapter that creates existing battle-engine objects from validated football profiles without wiring gameplay yet.

    Tradeoffs

    The adapter keeps legacy fields such as speciesId, types, currentHp, and moveTier so battle, save/load, and UI code remain unchanged. Football-specific naming stays deferred to later UI tasks.

    Design Decisions

    createPlayerInstance() reads profiles through DomainProfiles.getProfileOrThrow(), maps styles through DomainStyles.styleToLegacyType(), mirrors the existing HP formula, and exports only through window.DomainCombatAdapter.

    Risks / Follow-up

    Low integration risk because no caller has been rewired. P1-014 must explicitly decide when createInstance() delegates to the adapter and must verify no PokeAPI requests fire for football profile IDs.

Tradeoffs

Globals over imports Using browser globals preserves the no-build setup and minimizes boot risk. The cost is weaker dependency enforcement and more careful script order management.
Feature gates over deletion Gating Nuzlocke, cloud save, trade, and CCC is safer than removing code. The cost is temporary dead code that must not leak into the football UI.
Adapter over battle rewrite Creating football-shaped instances that match the old battle schema protects combat math. The cost is keeping fields like speciesId during Phase 1.
Lite settlement over full economy Album-only settlement proves retention without pulling in credits, fragments, or achievements. The cost is a smaller reward moment until Phase 3.
T0 silhouettes over real portraits CSS fallbacks avoid broken images and legal exposure. The cost is lower presentation quality for the first playtest.
Small reports over broad refactors Each task should leave the game playable. The cost is accepting some temporary duplication in UI paths until the vertical slice is complete.

Design Decisions Taken

  • Preserve engine semantics Keep battle damage, map DAG generation, team cap, boss win/loss flow, and current run persistence intact unless the active task explicitly changes them.
  • Prefer data-driven football content Players, host city bosses, and album layout should live in JSON catalogs. Code should load and validate those catalogs instead of embedding one-off player lists in UI handlers.
  • Use football branches inside existing screens For Phase 1, reskin starter, catch, swap, badge, and dex screens in place. Avoid creating an alternate UI framework or routing layer.
  • Make album writes monotonic Album state can move from unknown to seen to signed, never backwards. Settlement patches and direct mark calls should use the same rule.
  • Block invalid starts If catalogs are not loaded, starting a run is disabled. A visible loading/error state is better than falling through to legacy data.
  • Leave future systems unreachable Legend fragments, Run Budget, knockout, named events, achievements, and full meta settlement should not be partially implemented during Phase 1 tasks that do not request them.

Risk Notes

  • Script order remains fragile Because modules are plain scripts, a missing or misplaced script tag can break boot. Each task touching index.html should verify the title screen still loads.
  • UI terminology can leak The existing UI has many hardcoded Pokemon strings. The grep gate should be treated as a required identity check, not a polish step.
  • Save migration must be boring Migration should initialize structure only in Phase 1. It should not grant rewards, delete old keys, or mutate active runs.
  • Async catalog loading can race Any code path that renders starters, scouts, bosses, or album slots must assume catalog readiness is enforced before user interaction begins.

Guardrails For Future Task Work

Implement the requested task only. Before editing, confirm dependencies, name the affected files, and call out risks. After editing, validate the smallest playable path affected by the task. If a task requires an unfinished dependency, stop instead of filling in future work.
