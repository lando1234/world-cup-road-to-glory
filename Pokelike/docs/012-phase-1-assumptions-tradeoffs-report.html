Implementation report

SPEC 011 Phase 1 assumptions, tradeoffs, and design decisions

This report records the engineering assumptions made outside the written specs, plus the practical tradeoffs and localized design decisions that should guide Phase 1 implementation. Task-level entries should be appended as each SPEC 011 ticket lands.

Scope: Phase 1 vertical slice only No gameplay redesign Minimize file changes Working game after every task

Operating Assumptions

Task discipline

Each SPEC 011 task is treated as an isolated ticket. If dependencies are incomplete, implementation stops instead of partially building future work.

Compatibility first

The vanilla engine remains the source of truth for battle flow, map traversal, save/restore shape, and screen transitions unless a Phase 1 ticket explicitly changes the boundary.

Football-only slice

Phase 1 assumes football mode is the only player-facing experience. Legacy code may remain temporarily encapsulated during migration, but no Pokémon terminology or mechanics should remain visible in the slice.

Assumptions Outside The Specs

  • Node is the project automation baseline The playable app still runs through plain script tags, browser globals, and static JSON fetches, but project automation now uses package.json scripts. This gives Phase 1 repeatable validation without blocking the future Next/React migration path.
  • Domain modules use globals for now Because the existing app is not bundled, new domain modules should attach stable namespaces to window while keeping logic portable enough to copy into a future TypeScript domain layer.
  • Existing active saves may be imperfect Migration should be defensive for missing fields, but it should not try to convert an old active run into a football run. Fresh football runs are the supported Phase 1 path.
  • Catalog fetch errors are recoverable If JSON cannot load, the title screen should fail visibly and block new runs instead of falling back to Pokemon data or starting with incomplete football content.
  • CSS additions should be additive New football card, album, and stamp styles should avoid large rewrites of existing CSS. Legacy selectors can stay as long as football screens render correctly.
  • Player portraits come from TheSportsDB at runtime Phase 1 no longer depends on local /assets/players/{slug}.png files. Portrait URLs are baked into data/football/thesportsdb_portraits.json and merged into the profile catalog on boot. The free API key 123 is used for sync scripts only; gameplay reads static JSON to avoid rate limits.
  • Cutout PNG is the chosen portrait style strCutout (transparent ~500×500 PNG) is the active style via FEATURES.theSportsDbPortraitStyle: "cutout". strFanart1–4 were evaluated (16:9 promotional art) and rejected for battle/card layout; fanart fields remain in the map for optional future use.
  • Third-party likeness remains a legal risk TheSportsDB cutouts are real-player likeness from a third-party catalog, acceptable for internal slice demos only. Profiles declare legal.likenessTier: 0. Public release requires legal review and owned or licensed art — see “Temporary Bridges To Retire Later”.
  • Scripted validation and manual QA are both required Each task must include targeted validation. Domain work should extend Pokelike/scripts/validate-football-domain.mjs; UI and gameplay work should also use browser or HTTP smoke validation when the changed surface is visible. Automated screenshots are opt-in for now.
  • One task, one commit Every implementation task should end in a single atomic commit that includes implementation, validation, tests, task breakdown updates, assumptions updates, and any relevant Phase 2 visual-friction notes.

  • P1-014 — Guard PokeAPI paths for football profile IDs in data.js

    Status: implemented Review: PASS
    Assumptions

    When FEATURES.footballMode is true, numeric IDs 1-50 are reserved for football profiles even if the domain catalog has not loaded yet. They must not be interpreted as legacy Pokémon IDs.

    Tradeoffs

    The guard stays in data.js so existing callers in game.js and ui.js remain unchanged. This preserves flow compatibility but keeps a temporary bridge in the legacy data layer.

    Design Decisions

    fetchPokemonById() claims football IDs before static Pokédex, cache, or PokeAPI lookup. createInstance() claims direct IDs and profile/species-shaped objects before legacy instance construction, then delegates to DomainCombatAdapter.createPlayerInstance().

    Risks / Follow-up

    Dependency failures now fail loudly with descriptive errors instead of falling back to Ivysaur/Messi ID collisions. P1-015 can replace starter IDs next, but should verify the starter screen after catalog initialization.

  • P1-015 — Replace starter selection with football starters

    Status: implemented Review: PASS
    Assumptions

    The football starter trio owns STARTER_IDS in Phase 1: profileIds 1, 2, and 3 map to Mbappé, Messi, and Van Dijk. Legacy Gen 1 starters still need an explicit compatibility constant while football mode is active by default.

    Tradeoffs

    Adding LEGACY_STARTER_IDS preserves non-football Gen 1 behavior after STARTER_IDS becomes football-only. The cost is one extra transitional constant in data.js until the legacy Pokémon mode is fully separated or removed.

    Design Decisions

    showStarterSelect() now ignores state.gen2Mode when FEATURES.footballMode is true, so a saved Gen 2 toggle cannot bypass the football trio. Non-football mode keeps the previous Gen 1 / Gen 2 branch unchanged through LEGACY_STARTER_IDS and GEN2_STARTER_IDS.

    Risks / Follow-up

    Low runtime risk because starter rendering still uses fetchPokemonById(), createInstance(), and renderPokemonCard(). UI copy, Marquee Signing presentation, and Pokémon-themed badges remain intentionally deferred to later UI/theme tasks.

Temporary Bridges To Retire Later

These patterns exist to ship Phase 1 on the current no-build runtime. They are intentional shortcuts. Do not treat them as final architecture.

  • Browser globals on window

    Why now

    The app loads plain scripts without a bundler. Domain modules attach Domain* namespaces to window so data.js, game.js, and ui.js can call them today.

    Retire in

    Phase 2+ when the client moves to a typed module boundary (bundled app or explicit import graph).

    Target replacement

    ES modules or a typed domain package with explicit exports; no mutable global registries.

  • speciesId === profileId

    Why now

    The battle engine, save shape, and UI still key off legacy instance fields. Football instances mirror Pokémon instances so combat, team bars, and persistence work without a rewrite.

    Retire in

    Phase 2 when save migration and battle adapters accept a first-class profileId (or equivalent) on every football entity.

    Target replacement

    Football-native instance schema: explicit profileId, no overloaded speciesId for players; legacy Pokémon paths keep speciesId only.

  • styleToLegacyType()

    Why now

    getTypeEffectiveness() and move pools still consume legacy type strings. Styles project into the old chart so football combat works before native StyleId math lands everywhere.

    Retire in

    Target replacement

  • LEGACY_STARTER_IDS

Data Stability Rule

Every PlayerInstance must be serializable and restorable without live network calls.

Saved runs store stats, ids, HP, form level, and team composition — not portrait fetch state. Runtime portraits may request external URLs for display, but a failed or offline image must degrade to nation-code / silhouette UI only. Restore paths must never call TheSportsDB, PokeAPI, or any other remote service. If a portrait URL breaks after save, gameplay continues; only presentation changes.

Migration Guardrails

  • Never mutate active poke_current_run during Phase 1 migration Migration initializes missing football meta keys only. It does not rewrite an in-progress Pokémon run into a football run or alter team state mid-run.
  • Never dual-write poke_dex and game_album Album progress lives in the football album model. Phase 1 must not mirror catches into legacy Pokédex keys or keep two sources of truth.
  • Migration must be idempotent Running migration twice on the same save must produce the same result. No cumulative patches, no duplicate stamps, no escalating rewards.
  • No retroactive rewards during Phase 1 Migration adds structure, not loot. Signed album slots, credits, fragments, and achievement unlocks stay out of migration handlers until their spec tasks explicitly allow them.
  • Failed catalog load blocks new run start If player profiles, bosses, or required football JSON fail to load, the title screen shows a visible error and disables new campaigns. Silent fallback to Pokémon catalogs is forbidden.

Opinionated Summary

Phase 1 assumptions are acceptable because they keep the vanilla loop playable while football content lands incrementally. Globals, legacy field names, style projection, and remote cutouts are scaffolding — not the destination architecture.

Treat every bridge in this report as debt with an owner and a phase boundary. Ship the slice, validate fun, then retire shortcuts before widening scope or publishing. If a shortcut survives because it is convenient, document why and schedule the replacement; do not normalize it by silence.

Design Decisions Taken

  • Preserve engine semantics Keep battle damage, map DAG generation, team cap, boss win/loss flow, and current run persistence intact unless the active task explicitly changes them.
  • Prefer data-driven football content Players, host city bosses, and album layout should live in JSON catalogs. Code should load and validate those catalogs instead of embedding one-off player lists in UI handlers.
  • Use football branches inside existing screens For Phase 1, reskin starter, catch, swap, badge, and dex screens in place. Avoid creating an alternate UI framework or routing layer.
  • Make album writes monotonic Album state can move from unknown to seen to signed, never backwards. Settlement patches and direct mark calls should use the same rule.
  • Block invalid starts If catalogs are not loaded, starting a run is disabled. A visible loading/error state is better than falling through to legacy data.
  • Load portraits before validating catalog consumers portrait-source.js must load before profiles.js so catalog enrichment can run inside initCatalog(). Missing script tag breaks football portraits silently (local JSON paths remain).
  • Regenerate portrait map out of band Run node Pokelike/scripts/sync-thesportsdb-portraits.mjs after roster changes. Expect HTTP 429 if hammering the free API; script retries with backoff and uses lookup-by-id only.
  • Leave future systems unreachable Legend fragments, Run Budget, knockout, named events, achievements, and full meta settlement should not be partially implemented during Phase 1 tasks that do not request them.
  • Keep deferred visual debt visible Non-blocking sprite gaps, image issues, visual inconsistencies, and UX friction discovered during Phase 1 should be recorded in 013-phase-2-visual-frictions.html instead of being silently deferred.

Risk Notes

  • Script order remains fragile Because modules are plain scripts, a missing or misplaced script tag can break boot. Each task touching index.html should verify the title screen still loads.
  • UI terminology can leak The existing UI has many hardcoded Pokemon strings. The grep gate should be treated as a required identity check, not a polish step.
  • Save migration must be boring Migration should initialize structure only in Phase 1. It should not grant rewards, delete old keys, or mutate active runs.
  • Async catalog loading can race Any code path that renders starters, scouts, bosses, or album slots must assume catalog readiness is enforced before user interaction begins.
  • TheSportsDB: slice-only likeness shortcut Internal vertical slice only. Remote cutouts from TheSportsDB are not approved for public release without legal and licensing review. Club-kit PNGs are acceptable temporary presentation assets for demos; they are not canonical national-team art and must not ship as final player identity. Portrait URLs are display-only — saves never depend on them. Missing or broken images must always fall back to nation-code / silhouette UI; gameplay must never block on CDN success. Rate limits and ambiguous search (Rodri, Pedri overrides) affect sync scripts only, not runtime saves.
  • TheSportsDB sync and CDN operations Free-tier sync uses lookup-by-id and retries on HTTP 429. Gameplay reads baked JSON; live API calls happen only during out-of-band sync. Blocked or stale CDN URLs degrade presentation only — verify fallbacks in battle, team bar, and starter select.
